**作者：** 吴林斌（armaygooser）

**应聘方向：** FDE Intern

**项目类型：** AI 辅助的真实业务问题探索与可运行原型

**在线演示：** <https://armaygooser.site>

**源代码：** <https://github.com/armaygooser/duideshang>

## 摘要

“对得上”是一款面向广告制作门店的需求澄清、方案确认与可解释报价助手。它不把 AI 定位为替老板计算价格的工具，而是处理询价到施工之间最容易被忽略的信息断点：客户使用“三米左右”“正规一点”“大气一点”等自然表达，商家凭经验形成默认理解，双方直到成品交付时才发现预期不同。

项目的价值不只是输出一个价格，而是把客户原话、澄清问题、确认结果、价格组成、交付边界和验收标准连接成一个闭环。只有影响价格和交付的高风险字段全部确认后，后端确定性程序才允许生成正式报价。

这份报告重点记录我如何与 AI 协作：先发散出 10 个小微商家工具方向，再通过网络检索排除成熟赛道，随后连续质疑“老板不会算价”和“AI 可以替客户做决定”这两个错误前提，最终把项目从“询价转报价”收敛为“需求对齐、确认、报价与验收”。当前成果证明了软件闭环可以实现，但不虚构市场验证、用户访谈或商业收益。

## 一、任务背景与我的目标

繁星之宙给出的任务非常开放：从网页工具、AI 研究、生活改进方案或新技能学习中选择一个方向，借助 AI 完成，并在面试中分享思路、过程和收获。邮件特别说明，评价重点不是完成度，而是与 AI 协作及解决问题的方式。

我因此没有把目标设成“尽快生成一个看起来像产品的网页”，而是给自己增加了三个约束：

1. 先调查现有产品，不为了展示技术重复制造成熟工具。
2. 找到一个足够小、能够在一两天内实现，但又能暴露真实业务判断的工作流。
3. 让最终 Demo 同时展示问题定义、AI 协作、工程实现、风险边界和交付意识。

我希望证明的不只是“我会调用模型”，而是我能否像 FDE 一样进入具体场景，识别信息丢失和责任模糊的位置，把模糊需求拆成可验证的方案，并在有限时间内交付一个可以运行的闭环。

## 二、从 10 个候选方向开始

第一阶段我没有立即写代码，而是先列出 10 个面向小微商家的候选工具，并让 AI 帮我制定检索词、搜索代表产品、比较成熟度、数据壁垒、合规风险和一天内的可演示性。

| 候选方向 | 检索后的判断 | 没有选择的主要原因 |
|---|---|---|
| 民宿多平台房源打通 | 成熟赛道 | Channel Manager 已经能够同步多个 OTA 的房态、价格与库存；真正落地还依赖平台接口和商户授权 |
| 小店招聘私信整理 | 已有大量 ATS、简历解析和 AI 招聘能力 | 微信数据取得、隐私授权与招聘合规超出一天原型能诚实验证的范围 |
| 小店竞品价格侦查 | 成熟的价格监测与动态定价赛道 | 数据抓取、商品匹配、反爬和价格策略本身比生成建议更困难 |
| 个体户票据与报销整理 | 财税与 OCR 产品成熟 | 发票识别、自动填单、审核和归档已有完整产品；税务准确性风险高 |
| 小微老板合同避坑 | AI 合同审查已产品化 | 法律责任高，不能把通俗解释包装成可靠法律意见 |
| 社区小店拼单接龙 | 已有直接同类产品 | “群接龙”等产品已经覆盖团购、报名、门店自提等场景，差异化不足 |
| 小餐饮菜单利润体检 | POS、库存与餐饮成本系统已有能力 | 毛利计算本身简单，真实价值依赖持续、准确的采购与损耗数据 |
| 多平台差评客诉分析 | 成熟的声誉管理赛道 | 已有跨平台聚合、情绪与主题分析、AI 回复和审批流程 |
| 微信询价转报价 | CPQ/报价属于成熟能力，但自然语言澄清仍有缝隙 | 保留并继续缩小范围 |
| 老板想法转四象限待办 | 通用 AI 办公能力 | Notion AI 等工具已能总结、提取行动项和维护任务，场景过于宽泛 |

这次检索没有证明“市场上完全没人做询价工具”。相反，它让我放弃了追求绝对新颖的思路。绝对无人涉足可能意味着没有需求，也可能意味着数据、接口或合规成本太高。更合理的目标是：在成熟能力之间找到一个被忽略但可验证的工作流缝隙。

桌面调研只用于快速筛选方向，不等同于完整市场研究。它没有覆盖所有中国本地产品，也不能替代真实门店访谈。

## 三、为什么最后选择询价场景

“微信询价转报价”最初看起来只是把客户口语转换成结构化报价。这个方向容易演示，但一开始的价值假设并不成立。

我主动提出了第一个反问：

> 熟练店家通常很快就能估出价格，为什么还需要 AI？

这个问题迫使我和 AI 放弃“节省几分钟计算时间”的浅层叙事。继续分析后，我认为报价工具仍有两个价值：

- 把总价拆成客户看得懂的项目、假设与边界，使价格更透明，减少反复解释。
- 把客户口语转换成完整规格，让价格对应明确需求，而不是对应老板脑中的默认方案。

随后我提出了第二个、也是决定项目方向的判断：

> 核心痛点不是算价，而是对接。系统必须找出客户需求中不清晰的部分，逐项确认，防止做出来以后客户不满意。

例如客户说“字体正规一点”，老板可能直接默认黑体，但客户想象的是宋体。这里即使老板成本计算准确、施工质量合格，交付仍然会失败。Agent 不应把自己的推断写成客户需求，而应该继续问：客户更接近稳重正式的宋体、简洁现代的黑体，还是其他视觉风格？

项目因此经历了三次收敛：

```text
快速报价工具
  -> 可解释报价工具
  -> 需求对齐、确认、报价与验收闭环
```

最终核心问题被定义为：如何在成本最高的返工发生以前，让客户表达、商家理解和最终验收“对得上”。

## 四、为什么把场景限定为广告门头制作

我没有继续做一个适用于所有小商家的通用 Agent，而是把 MVP 限定到广告制作门店的门头询价，原因是：

- 客户经常使用“正规”“大气”“高级”等主观语言。
- 尺寸、材料、发光结构、安装高度和交期都会影响价格与施工。
- 成品属于物理交付，理解偏差会造成真实返工成本。
- 需求能够被拆成字段、确认记录、报价规则和验收标准。
- 可以使用明确标注的演示价目完成原型，不必假装掌握真实市场统一价格。

这个范围足够小，可以在有限时间内实现；同时又足够真实，能够展示需求理解、业务建模、Agent 边界、确定性计算和交付验收。

## 五、我与 AI 的协作过程

### 5.1 AI 作为发散与检索助手

我先提供候选问题和筛选标准，让 AI 补充检索词、寻找代表产品并建立比较维度。AI 帮助我快速看到：房态同步、票据 OCR、合同审查、评价聚合等方向并不是空白市场，而且很多方向的核心门槛是平台连接、合规或数据质量，不是做出一个页面。

这个阶段 AI 提高了信息覆盖速度，但“是否放弃一个方向”由我决定。我没有把搜索结果直接当作市场结论，而是把它当成风险地图。

### 5.2 AI 作为反方，而不是答案生成器

选择询价方向后，我没有直接要求 AI 写 PRD，而是不断挑战初始假设：

- 老板已经会快速估价，工具还创造什么价值？
- “透明报价”是否会错误地暴露采购成本和利润？
- 如果 AI 自动选择了字体或材料，客户不满意时谁负责？
- 客户不懂“亚克力正面发光字”等术语，追问怎样才能让他做出选择？

这些问题推动产品形成四条原则：

1. 透明的是报价组成、计价假设和不包含项目，不是商家的采购底价与利润。
2. 客户原话、AI 推断和商家建议必须分开显示。
3. AI 不能把建议自动改成“客户已确认”。
4. 高风险字段未确认时，系统不能生成正式报价。

### 5.3 AI 作为规格与行业知识整理助手

问题定义稳定后，我让 AI 协助把业务流程写成可开发规格：需求字段状态、风险等级、澄清顺序、报价解锁条件、价格来源、验收模板和变更历史。

行业知识没有使用向量数据库，而是整理为可读、可审计的 YAML：产品类型、材料、歧义词典、澄清规则、报价规则和验收标准。这样做不是因为 RAG 无用，而是因为当前数据量小、规则需要人工审核，并且正式报价不能依赖不可解释的相似度检索。

### 5.4 AI 作为编码协作者

我确定技术栈为 Next.js、FastAPI 和 shadcn/ui，并要求同时支持真实 DeepSeek Provider 与不需要密钥的本地演示 Provider。AI 辅助完成了：

- 前后端代码骨架和类型模型。
- 受控 Agent 工具与 Pydantic 输出校验。
- 确定性报价引擎和报价锁定规则。
- 三栏工作台、需求确认、变更记录与打印界面。
- 前端状态测试、后端 API 与 Provider 测试。
- README、架构、部署、演示和局限文档。

我负责持续检查生成结果是否符合业务原则。例如我否定了让模型直接计算正式价格、把 AI 建议当成确认、为了“智能”引入不必要向量数据库，以及虚构用户访谈和效率数据等做法。

### 5.5 AI 作为验证与部署协作者

开发结束后，我让 Codex 执行 lint、类型检查、测试和生产构建，而不是只确认页面能打开。前端 5 个测试、后端 9 个测试通过，生产构建完成。

部署过程也出现了真实问题：Vercel 最初把 FastAPI 项目识别为 Other，虽然界面显示 Ready，但构建日志没有 Python Function。我和 AI 没有停在“平台显示成功”，而是继续检查构建产物，补充根级入口、标准 Python 项目元数据和 FastAPI Framework Preset，最终确认生成了实际的 FastAPI Function。

GitHub 首次推送时，Push Protection 还拦截了环境变量示例中的密钥形态内容。我没有绕过保护，而是清理示例、重写尚未发布的 commit，并确保简历、招聘邮件、真实 `.env`、临时日志和 Vercel 本地元数据不会进入公开仓库。这次纠错让我进一步认识到，AI 加速开发的同时也必须配合最小权限、密钥隔离和发布前检查。

最后，考虑到 `.vercel.app` 在中国大陆网络中的不确定性，我申请并配置了自定义域名，同时保留本地演示与录屏作为降级方案。

## 六、哪些判断来自我，哪些工作交给 AI

| 我的职责 | AI 的职责 |
|---|---|
| 提出候选问题与时间约束 | 扩展检索词并整理代表产品 |
| 质疑“老板不会算价”的前提 | 从透明度、信任和交付角度继续分析 |
| 把核心痛点定义为需求对接 | 将痛点拆成字段、流程和界面状态 |
| 选择广告门头作为 MVP 边界 | 整理材料、澄清问题和验收规则草稿 |
| 决定 AI 不得自动确认或正式算价 | 生成受控工具、校验和 Provider 实现 |
| 审查功能真实性与产品边界 | 辅助编码、测试、文档与部署排错 |
| 决定展示内容并完成最终验收 | 根据反馈快速修改和补齐交付物 |

我没有把 AI 当作一次性生成器，而是把它分别放在研究、反驳、规格、实现和验证角色中。人的主要价值不是逐行手写所有代码，而是持续提供目标、约束、反例和验收标准，并对最终结果负责。

## 七、产品工作流

1. 店员复制客户微信询价。
2. Agent 引用原文，提取明确需求并标记歧义与缺失项。
3. 系统按返工风险和价格影响排列澄清问题。
4. 客户或店员逐项确认字体、发光结构、尺寸、安装、交期等字段。
5. 确认单实时更新；高风险项未确认时正式报价保持锁定。
6. 后端按 YAML 演示价目确定性计算报价。
7. 系统输出报价组成、假设、不包含项目、验收标准和微信确认话术。
8. 修改已确认字段时留下变更记录，并使旧报价失效。

桌面端采用三栏结构：左栏保留客户原话与证据；中栏展示澄清问题和客户能理解的选项；右栏持续显示确认状态、正式报价和验收标准。

## 八、Agent 与确定性程序的边界

Agent 负责语言理解：提取需求、识别歧义、查询只读行业知识、生成问题和复述结果。

程序负责业务约束：字段状态、报价解锁条件、价格计算、版本记录和验收模板组合。

这种拆分保证：

- 模型不能凭空创造材料单价。
- 相同确认输入产生相同金额。
- AI 推断不能伪装成客户确认。
- 外部模型不可用时，核心工作流仍能通过本地 Provider 演示。
- 正式报价始终保留人工复核入口。

## 九、技术架构与工程结果

```text
Next.js + TypeScript + shadcn/ui
          |
          | REST
          v
FastAPI + Pydantic + Provider Manager
          |
          +-- DeepSeek Agent（可选）
          +-- 本地确定性演示 Provider（默认与降级）
          |
          v
YAML 行业规则 + 确定性报价引擎
```

当前已经验证：

- 前端 lint、类型检查、5 个状态测试和生产构建通过。
- 后端 Ruff、9 个 API/Provider 测试通过。
- 无模型 API Key 时可以完成完整演示。
- 外部模型超时或结构校验失败时自动降级。
- 报价单价来自 YAML 规则，而不是模型输出。
- 需求变更会留下记录并要求重新生成报价。
- Next.js 前端和 FastAPI 后端分别部署到 Vercel。
- 自定义域名已完成解析并可直接访问。

这里验证的是软件行为和交付链路，不是商业价值。

## 十、我在这个项目中的收获

第一，AI 最有价值的地方不只是生成内容，而是扩大搜索范围、快速建立比较框架，并在明确约束后加速实现。

第二，一个看起来合理的需求可能建立在错误前提上。“快速报价”听起来有用，但如果店家本来就能快速估价，就必须继续追问真正的损失发生在哪里。

第三，Agent 不应隐藏不确定性。客户原话、AI 推断和人工建议分开，可能比模型给出一个自信答案更重要。

第四，物理交付场景不能只做聊天界面。需求必须最终进入价格规则、交付边界、验收标准和变更记录。

第五，工程上的 Ready 不等于真正可用。部署产物、网络访问、密钥、降级方案和面试现场备用路径都属于交付的一部分。

## 十一、局限与下一步

当前版本仍有明确边界：

- 行业价格是演示门店内部价目，没有经过真实门店核价。
- 没有开展真实客户访谈，也没有返工率或成交率数据。
- 文字确认不能代替现场复尺、承载、电气安全和审批判断。
- 视觉偏好仍需要效果图、色样或实物样品确认。
- localStorage 不适合多人协作和长期审计。
- 当前不支持微信接入、支付、签约、图片测量和多商户权限。

如果再给一周，我不会先增加更多 AI 功能，而会：

1. 访谈 3-5 家广告制作门店，收集匿名化询价样本和真实返工原因。
2. 让店员分别用原流程和原型处理相同询价，记录追问次数与漏项。
3. 测试客户一次愿意回答多少问题，优化澄清顺序。
4. 让施工负责人审核必问字段、价目规则和验收模板。
5. 增加效果图、尺寸标注和客户签字确认。
6. 只有验证有效后，再建设账户、数据库、微信接入和多行业模板。

## 十二、为什么这个过程与 FDE 有关

我对 FDE 的理解不是拿一个固定产品寻找客户，而是进入真实工作流，理解客户说了什么、没有说什么、哪些信息会影响交付，再把问题拆成能够实现和验收的系统。

这个项目希望展示的不是“我能用 AI 做一个报价网页”，而是：

> 我能够持续质疑最初的问题定义，找到信息丢失和责任模糊的位置，再把 AI、确定性程序和人工确认组合成一个可运行、可解释、可验收的最小闭环。
