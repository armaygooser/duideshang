# 《对得上》项目报告

## 摘要

“对得上”是一款面向广告制作门店的需求澄清、方案确认与可解释报价助手。项目不把 AI 定位为替老板计算价格的工具，而是处理询价到施工之间最容易被忽略的信息断点：客户使用“正规一点”“大气一点”“三米左右”等自然表达，商家凭经验形成默认理解，双方直到成品交付时才发现预期不同。

产品将客户原话拆分为明确需求、歧义项、缺失项和未经确认的建议，按返工风险发起澄清，并把专业选择转化为客户能够理解的文字和视觉选项。只有高风险字段全部确认后，后端确定性程序才生成报价、交付边界和验收标准。

当前版本是一个可运行的面试原型。它证明了完整工作流能够被实现，但不声称已经验证商业效果。

## 一、问题是如何被重新定义的

最初设想是“微信询价转报价”：解析客户的口语询价，帮助小商家快速输出报价。继续拆解后发现，熟练店家通常并不缺少估价速度，他们真正缺少的是把脑中的经验判断转化为客户能够理解、确认和追溯的规格。

例如客户说：

> 想做个三米左右的门头，正规大气一点，要能发光，预算四五千，下周五前弄好。

“正规”可能被理解为宋体、黑体或机构门牌风格；“大气”可能指字号、间距、材质厚度或发光方式；“下周五前”也可能分别指设计完成、制作完成或安装验收。如果老板直接采用自己的默认理解，即使计算和施工都没有错误，客户仍可能认为“这不是我想要的”。

因此项目经历了三次收敛：

```text
快速报价工具
  -> 可解释报价工具
  -> 需求对齐、确认、报价与验收闭环
```

最终核心问题被定义为：如何在成本最高的返工发生以前，让客户表达、商家理解和最终验收“对得上”。

## 二、市场调研与切入缝隙

调研发现，民宿多平台房态、合同审查、发票整理、评价分析、餐饮毛利等方向已经存在成熟产品。单纯生成报价也属于 CPQ/CRM 的成熟能力。

本项目没有宣称创造一个全新赛道，而是选择成熟系统覆盖不足的狭窄工作流：小微商家的业务往往从微信口语开始，客户不具备填写标准技术表单的专业知识，门店也不会为了一次询价引入完整企业系统。

项目的差异不在“是否能生成报价”，而在：

- 找出自然语言中可能造成返工的歧义。
- 将专业术语变成客户能做决定的选项。
- 区分客户原话、AI 推断和商家建议。
- 在报价前形成确认，在交付前形成验收依据。
- 保留需求变更历史，避免口头约定失去上下文。

这是一项待验证的产品假设，而不是已经证明的市场结论。

## 三、目标用户与工作流

MVP 只面向广告制作门店的门头询价，不做多行业平台。

典型流程：

1. 店员复制客户微信询价。
2. Agent 引用客户原文，提取明确需求并标记歧义与缺失项。
3. 系统按返工风险和价格影响排列澄清问题。
4. 客户或店员逐项确认字体、发光结构、尺寸、安装、交期等字段。
5. 确认单实时更新；高风险项未确认时正式报价保持锁定。
6. 后端按 YAML 内部价目确定性计算报价。
7. 系统输出报价组成、假设、不包含项目、验收标准和微信确认话术。
8. 修改已确认字段时留下变更记录，并使旧报价失效。

## 四、产品设计

桌面端采用三栏结构：

- 左栏保留客户原话和证据，高亮明确、模糊和缺失信息。
- 中栏展示澄清问题以及客户能够理解的选择卡片。
- 右栏持续显示需求确认状态、风险和正式报价是否可用。

例如“正规一点”不会被简单转换为“请选择黑体或宋体”，而是展示：

- 稳重正式：类似机构门牌的宋体风格。
- 简洁现代：笔画均匀、远距离清晰的黑体风格。
- 传统文化：具有书写感的书法风格。

设计重点不是让 AI 代替客户做决定，而是降低客户做出明确决定所需的专业门槛。

## 五、Agent 与确定性程序的边界

Agent 负责语言理解：提取需求、识别歧义、查询只读行业知识、生成问题和复述结果。

程序负责业务约束：字段状态、正式报价解锁条件、价格计算、版本记录和验收模板组合。

这种拆分解决了三个问题：

- 模型不能凭空创造材料单价。
- 相同确认输入产生相同金额。
- 即使外部模型不可用，核心演示仍可以通过本地 Provider 完成。

真实 DeepSeek Agent 最多执行四轮受控工具调用，只能查询产品、材料、歧义和澄清规则。服务端使用 Pydantic 校验输出，移除不在客户原话中的伪造引用，并禁止模型把未经客户操作的字段标记为已确认。

## 六、技术架构

```text
Next.js + TypeScript + shadcn/ui
          |
          | REST / SSE
          v
FastAPI + Pydantic + Provider Manager
          |
          +-- DeepSeek Agent（可选）
          +-- 本地确定性演示 Provider（默认与降级）
          |
          v
YAML 行业规则 + 确定性报价引擎
```

前端保存当前会话和变更历史；MVP 没有账户与数据库。FastAPI 再次校验报价所需字段，避免只依赖前端按钮锁定。部署采用同一仓库的两个 Vercel Project：Next.js 前端和 FastAPI 后端。

## 七、行业知识库

知识库采用可读、可审计的 YAML，而非向量数据库，当前覆盖：

- 亚克力正面发光字。
- 不锈钢背发光字。
- PVC 字。
- 灯箱门头。
- 模糊表达词典。
- 澄清优先级规则。
- 报价规则和计价覆盖范围。
- 验收模板与六个演示案例。

所有数值都明确标记为“演示门店内部价目”，没有冒充市场统一价格。真实商用前必须由具体门店、供应商和施工负责人审核。

## 八、AI 协作过程

AI 被用于四类工作：

1. 发散并比较小微商家工作流点子。
2. 检索竞品，排除已经高度成熟或接口壁垒过高的方向。
3. 帮助把“报价速度”继续追问为“信任、需求确认和交付边界”。
4. 在明确产品规格后协助实现前后端、规则库、测试和文档。

人的关键判断包括：

- 否定“商家不会算价”的错误前提。
- 将透明理解为交付项目和假设透明，而不是暴露采购成本和利润。
- 发现“正规一点”等表达不能靠行业术语追问，必须提供可理解选项。
- 限制模型权限，让正式报价继续由确定性程序和人工复核控制。
- 不虚构用户访谈、节省时间或商业转化数据。

## 九、已经验证的工程结果

- 后端包含报价锁定、确定性计算和 Provider 边界测试。
- 前端包含确认状态、去重和下一问题选择测试。
- 无模型 API Key 时可以完成完整演示。
- 外部模型超时或结构校验失败时自动降级。
- 报价单价来自 YAML 规则，而不是模型输出。
- 需求变更会留下记录并要求重新生成报价。

这里验证的是软件行为，不是商业价值。

## 十、局限与风险

- 当前只有模拟行业数据，未经过真实门店核价。
- 没有开展真实客户访谈，也没有返工率或成交率数据。
- 文字无法代替现场复尺、墙体承载、电气安全和审批判断。
- 视觉偏好仍需效果图、色样或实物样品确认。
- localStorage 不适合多人协作和长期审计。
- 当前不支持微信接入、支付、签约、图片测量和多商户权限。
- 模型仍可能漏项，因此原文证据、人工确认和后端规则边界不能取消。

## 十一、如果再给一周

下一阶段不应优先增加更多 AI 功能，而应验证问题是否真实存在：

1. 访谈 3-5 家广告制作门店，收集匿名化询价样本和真实返工原因。
2. 让店员分别用原流程和原型处理相同询价，记录追问次数、漏项和完成时间。
3. 测试客户一次最多愿意回答多少问题，优化澄清顺序。
4. 让施工负责人审核必问字段、价目规则和验收模板。
5. 增加最终效果图、尺寸标注和客户签字确认。
6. 只有验证有效后，再建设账户、数据库、微信接入和多行业模板。

## 十二、面试展示结论

这个项目希望展示的不是“我能用 AI 做一个报价网页”，而是：

> 我能够进入真实工作流，持续质疑最初的问题定义，找到信息丢失和责任模糊的位置，再把 AI、确定性程序和人工确认组合成一个可运行、可解释、可验收的最小闭环。
